# QQ 本地守护、检查与停止

2026-10-14：新增本机 QQ 守护，仅管理当前项目的 QQ 工作进程，不接管 MySQL、网页、API 或其他程序。

## 日常操作

保持原 MySQL 与网页服务运行。可以在文件管理器中双击：

| 文件 | 用途 |
| --- | --- |
| `scripts/start-qq.cmd` | 后台启动 QQ 守护，意外退出时恢复 QQ 进程 |
| `scripts/check-qq.cmd` | 显示守护、QQ 进程、QQ 连接、数据库及本机 API 状态 |
| `scripts/stop-qq.cmd` | 主动停止 QQ 守护与工作进程，停止后不再自动拉起 |

命令行等价操作（项目根目录）：

```powershell
.venv/Scripts/python.exe -X utf8 scripts/qq_service.py start
.venv/Scripts/python.exe -X utf8 scripts/qq_service.py status
.venv/Scripts/python.exe -X utf8 scripts/qq_service.py stop
.venv/Scripts/python.exe -X utf8 scripts/qq_service.py restart
```

`status --json` 提供结构化结果。启动成功表示守护已启动，QQ 是否连接成功仍应查看检查结果或 App 工作台。API 正常不等于 QQ 在线；健康检查也不代表实际消息已到达客户端。

## 恢复与停止规则

- 网络断线由现有 WebSocket 重连机制处理；守护只在工作进程退出后重新启动。
- 连续退出采用递增等待，默认 2、4、8、16 秒；连续 5 次失败后暂停恢复，避免循环启动。稳定运行 60 秒后重新累计连续失败。
- 配置缺失／重复进程的退出码 2 直接暂停。排除原因后手动 `restart`，不会自行修改密钥或权限。
- 主动停止写入当前实例的停止请求，等待工作进程取消任务并退出。恢复等待期间也响应停止。任务退出较慢时显示正在停止，不会强杀或重新拉起。
- 守护意外退出时，工作进程在守护心跳失效后退出，默认约 20 秒；新启动不会因为旧 PID 文件而杀错其他程序。
- 守护与工作进程分别使用系统文件锁防重复启动；停止请求只对当前实例有效。旧停止请求不会停止新实例。
- 发现旧的手动 QQ 进程时，不强制接管、不重复启动。首次切换需先确认并停止旧进程，再使用守护入口。保存的 PID 只用于诊断，不作为任意结束进程的依据。

## 消息保护

守护恢复的是进程，不代替业务层补发。原有事件去重、发送窗口和次数限制保持有效；结果不明的消息不自动重发。被中断的 `sending` 在原有恢复流程中转为结果待核对，`pending` 仍绑定原客户消息及回复窗口，不借新消息补发旧内容。

正常停止会等待正在写入的心跳完成后记录停止，避免迟到的旧心跳覆盖停止状态。进程被强制结束时，工作台仍依靠心跳超时识别离线。

## 日志与故障排查

2026-10-16 修订：状态文件原子替换在短暂重试后仍可能遇到 Windows 文件访问错误。守护现在记录 `state_write_deferred` 并继续监督工作进程，下一轮尝试写入，不因一次状态写入失败直接退出。没有成功保存的心跳不视为有效，工作进程的原有 20 秒租约保护保持不变。

每次启动工作进程之前，必须成功保存当前实例的状态和新鲜心跳；写入持续不可用时至多等待约 20 秒（另加单次文件重试耗时），记录 `launch_blocked_by_state_write` 并停止启动，不使用旧实例状态拉起子进程。主动停止仍按原实例令牌处理，不放宽文件权限、不绕过锁，也不安装系统自启动。

忽略目录 `.local/qq/`：

- `service.log`：启动、退出码、运行时长、恢复等待和暂停原因，1MB 轮转、保留 3 份备份。
- `gateway.log`：现有网关日志，超过约 2MB 后在进程之间轮转、保留 3 份备份；文件占用时延后轮转，不因此阻止连接。
- `service.json`：当前实例、心跳、重启计数及最近退出记录；不存密钥。
- `stop-request.json`、锁文件：用于当前实例的协作控制。不要通过删除锁文件强行绕开运行中的进程。

日志和状态不提交；不要分享 `backend/.env`。检查命令仅显示状态与异常类型，不输出数据库密码、QQ 密钥、访问凭证或平台响应正文。

检查显示数据库不可用时，先恢复数据库；API 不可用时检查原网页服务。QQ 恢复已暂停时先查 `service.log` 的退出码及 `gateway.log` 的错误类型，处理后再手动重启。

## 电脑重启

本功能未安装 Windows 服务、登录任务或开机自启动项。电脑重启后，先按原流程启动项目 MySQL 和网页，再双击 `start-qq.cmd`。关闭电脑、退出 Windows 或守护本身崩溃后，不能承诺自动恢复守护。安装系统级自启动可另行安排。

## 验证范围

使用独立临时目录与模拟工作进程验证：实际子进程异常退出后恢复、重复启动保护、主动停止与等待期间停止、连续失败暂停、配置失败暂停、旧停止请求隔离、守护进程死亡后工作进程自行退出。测试不向真实 QQ 发消息、不读写生产会话。

同时回归 QQ 网关、发送保护及状态接口。启动与连接检查不代替 QQ 客户端真实收发或手机后台验收。

2026-10-14 验证结果：45 项相关自动检查通过。本机已从旧手动进程切换为守护；确认真实连接和新鲜心跳，重复启动保持同一实例，主动停止后维持停止，随后重新启动并恢复 QQ 连接。异常崩溃恢复使用独立模拟进程验证，未故意让真实机器人崩溃。

2026-10-16：用户反馈真实 QQ 转人工无回复、App 无待接手会话；检查发现守护与工作进程均停止，日志有 `PermissionError` 和守护心跳失效提示，最近 30 分钟无 QQ 用户消息入库。原日志没有失败路径，不能断言每次访问错误均发生在同一文件操作；本次修复可复现的状态写入异常导致守护退出的路径。新增瞬时失败容错及启动前写入保护检查，守护与通道状态共 21 项通过（1 条现有弃用提示）。真实通道恢复和心跳复查见[故障记录](./QQ通道中断排查记录_2026-10-16.md)，用户补发消息和 App 收到交接仍须另行确认。
